# Agent instructions

## Building & testing

* On mac, build with `./build.sh` — produces `./bin/nova`
* After building, use `nova` in terminal for testing
* Use `nova config view` for getting configured values (instance, host, Nucleus server, etc.); tokens are redacted, add `--show-secrets` only when you really need one
* Test with a throwaway `HOME` (e.g. `HOME=$(mktemp -d) ./bin/nova …`) when a command writes the config, so the user's `~/.nova/config.yaml` stays untouched
* The command reference is not committed: it lives on the CLI reference site (GitHub Pages, deployed by the release workflow for stable releases). Look up commands with `nova <command> --help`.
* Site build: `hack/docsite/build.sh [version]` → `_site/`. Generates markdown into a temp dir (`go run . gendoc` alone writes to the gitignored `_docs/`) and renders it with `hack/docsite` (goldmark + template styled with `@wandelbots/design-tokens` / `@wandelbots/fonts`, vendored from npm at build time — bump the pinned versions in `build.sh`).

## Output (ADR `docs/decisions/0010-cli-contract.md`)

* stdout carries only a command's data; progress, warnings and child-process output go to stderr. Write data with `fmt.Fprint*(cmd.OutOrStdout(), …)`: cobra's `cmd.Print*` writes to **stderr** (only use it for messages). Library packages write messages to `os.Stderr`.
* `--debug` / `NOVA_DEBUG=1` (`pkg/debug`): logs target resolution, HTTP traffic (in `httpx`'s transport, so build HTTP clients with `httpx.Client()`/`httpx.Transport()`) and external commands (use `debug.Command` instead of `exec.Command`). Known secrets are redacted with `debug.Redact*`, but only as best effort: bodies can still carry secrets (app env, kubeconfigs), so review the output before sharing it (like `curl -v`). Never log a secret through `debug.Logf` unredacted; don't enable debug in CI.
* Long-running tools whose progress the user should see (docker/podman build and push, ssh import) run through `execx.Run` (`pkg/execx`): output streams to stderr, and when stderr is no terminal (agents, CI) the error carries the last 20 lines, e.g. the failing build step. On a terminal the tool keeps its TTY.
* Contract tests: `runAsProcess` in `pkg/cmd/output_contract_test.go` captures the real stdout/stderr (`runWithConfig` sets both writers and can't tell them apart).

## Instances (ADR `docs/decisions/0016-named-instances.md`)

* `~/.nova/config.yaml` holds a list `instances` (name, `kind`: `cloud` | `host` | `k8srun`, host, cellname, id, kubeconfig) plus `current-instance`. Global settings (editor, image-registry, container-runtime, catalogs, portal login `token`) stay top-level.
* Target resolution: `--instance <name>` → `NOVA_INSTANCE` → `current-instance`. An unknown name is an error, never a fallback. Resolving never writes the config. Use `--instance` instead of `nova instance select` when working in parallel with other sessions.
* Code reads the target via `currentHost()` / `currentCell()` / `currentTarget()` (`pkg/cmd/target.go`), never `viper.GetString("host")`. Registry logic: `pkg/instances`. Commands that manage the registry themselves or don't talk to an instance (`nova simulation`) carry the `annotationNoTarget` annotation.
* Legacy configs (bare top-level `host`) are migrated in memory into an entry `default` and persisted on the next write; legacy keys are kept and `host`/`cellname`/`virtualid` are mirrored from the selected entry for older CLI versions.
* Portal logins are per environment (`logins.<env>`, `default-env`; legacy `token` mirrors the default). The environment of an invocation: `--env` → `NOVA_ENV` → cloud target's `env` → default → `prod`, set once via `oauth.SetActiveEnvironment` (`pkg/cmd/target.go`); `oauth.LoadToken()` returns that environment's login. A plain `nova login` logs in to that same environment (only `--env` switches the default). The bearer token is only attached to `*.wandelbots.io` hosts (`oauth.SendsTokenTo`), never to `host`/`k8srun` instances.
* `nova instance kubeconfig [name]` prints the kubeconfig path (k8srun: stored; host: fetched once over ssh via `pkg/remote`, or imported with `--kubeconfig <file|->`; a loopback server is rewritten to the host); `nova instance env [name]` prints `NOVA_INSTANCE`/`KUBECONFIG` exports for `eval`, in the syntax of the calling shell (parent process, then `$SHELL`; `--shell` overrides). Never print kubeconfig contents. Code: `pkg/cmd/kubeconfig.go`.
* `nova instance add/remove` manage local entries; `create/delete/start/stop` are cloud-only. `instance create` and `k8srun create` select the new entry; `--no-select` only adds it (parallel sessions), target it with `--instance`. `extend` and `keep-alive [name] [-- cmd]` (ADR-0017, `pkg/cmd/keepalive.go`) work for cloud and k8srun: they extend only within `--margin` of the expiry and always read the new expiry back. Portal extend (`PUT /v1/instances/{id}/lifetime`, 201) takes no duration: now + the deployment's `expiryHours` (prod/stg 168 h, dev 24 h; source `developer-portal/portal-api` on code.wabo.run, values in `developer-portal/applications`); a deleted instance shows status `deleting` (not in the spec). k8srun sets 12 h and tracks the expiry itself (the service doesn't report it). With a command, keep-alive passes on its exit code (`exitCodeError` in `root.go`). `nova k8srun` (formerly `nova virtual`) creates named Kubernetes clusters with a kubeconfig. It is public in the CLI but the service is Wandelbots-internal (Wandelbots network only); its purpose is workflows that need the Kubernetes API (skaffold, helm, kubectl) when no device is at hand — keep that framing in help texts. `nova instance prune` drops `cloud` entries the portal no longer lists in their environment (one listing per environment, with that environment active) and `k8srun` entries as `k8srun prune`; `host` entries are never pruned. `nova k8srun prune` drops entries whose cluster is gone: only a 404 from `GET /instance/{id}/kubeconfig` counts (the service's OpenAPI is at `/openapi.json`), any other answer keeps the entry.

## Config file writes (`pkg/configfile`)

* Shells, agents and long-running commands (`nova mcp`, keep-alive) share `~/.nova/config.yaml`. Never call `viper.WriteConfig()`: it writes the process's whole, possibly minutes-old copy over the file (lost update) and truncates it first. Every write goes through `configfile.Update(v, func(disk *viper.Viper) error)` or `configfile.Set`: lock (`config.yaml.lock`), read the file as it is now, apply the change to `disk`, replace the file atomically, then `v` re-reads it. Don't `viper.Set` persisted keys on the global config either: an override hides later changes of the file. `TestNoDirectConfigWrites` enforces the first rule.
* The function runs under the lock: keep it short (the token refresh is the one request made there, on purpose: two processes must not refresh with the same refresh token), and never nest two updates.
* Lists of named entries (`instances`, `nucleus-servers`) are merged, not replaced: `Registry.Save` applies what this process added, changed or removed since `Load` to the file's current list (`configfile.Merge3`), and writes the selection only if it was changed here. So `Load` → long operation (instance create) → `Save` is safe without holding the lock.
* Older CLI versions still truncate and rewrite without the lock; `Update` and `configfile.Reload` wait up to a second for an empty file to get its content.
* The lock file and the temporary file live next to the config, so `~/.nova` must be writable (a writable `config.yaml` in a read-only directory no longer works).

## `nova api` (ADR-0013)

* `nova api <path>` like `gh api`; the path is complete (`/api/v2/cells/{cell}/...`, app paths work too), only `{cell}` is filled. `nova api search <words>` / `nova api schema <operationId>` read the v2 spec (`/api/v2/ui/public.openapi.yaml`, cached in `~/.nova/cache/api/<host>/<NOVA version>.json`). Code: `pkg/novaapi`, `pkg/cmd/api.go`.
* No guard rails (ADR-0009 addendum 2026-11-09): requests go out as given. Agent-safety labels belong in the spec (`x-…` extension, owned by the platform team), not in the CLI.
* Answers stream through as they arrive (`novaapi.PeekStart` only waits for the first bytes; never `Peek(n)` on a body). Long polls work (`--timeout 0`). WebSocket streams (`x-serverstream`/`x-bidistream`) are refused: exit 3, typed JSON error on stderr when it is no terminal (`typedError`/`printTypedError` in `pkg/cmd`). Streams get dedicated commands later (ADR-0013 notes).
* E2E: `testdata/api/e2e.sh` (CI job `e2e`, after the app install, with `NOVA_API_E2E_APP=your-nova-app`): v2 reads, collider round trip, errors, stream refusal, and the installed app's own API (`/{cell}/<app>/programs` from NOVAx). Runs locally against any instance with a cell, a controller and an app: `PATH=$PWD/bin:$PATH testdata/api/e2e.sh`.
* Ingress quirks (401 page with HTTP 200, JSON error page, login redirect) live in `pkg/ingress`; use it for any new instance client.

## App install: `--copy-image` (registry-less)

* `nova app install <app> --copy-image --ssh-user <user>` builds locally, copies the image to the configured `host` over ssh/scp, and imports it into the instance's k3s containerd — no registry push. Works with docker and podman (auto-detected).
* Only layers missing from the target's containerd content store are transferred; on any error it falls back to whole-image transfer.
* `--setup-ssh-key` (one-time per instance): installs the local ssh key + a k3s-scoped NOPASSWD rule in `/etc/sudoers.d/nova-cli`. The single sudo prompt during setup is the unavoidable bootstrap (needs sudo once to grant passwordless sudo); installs afterwards are prompt-free.
* Target needs sudo for `ctr` (containerd socket is root-only); k3s is invoked by absolute path so the NOPASSWD rule matches. Use `--no-sudo` for root logins.
* Code: `pkg/cmd/app.go` (`installAppViaCopy`/`copyIncremental`/`copyWholeImage`), `pkg/remote/` (ssh/scp + `setup.go`), `pkg/docker/` (`BuildImageOCI`, `save.go`, `ocilayout.go`).

## App templates: local dev settings (`nova app update-env`)

* Templates live in `pkg/generator/<Type>App` (`*.tpl` files are rendered, `__Field__` folders renamed). Generated projects keep instance url, cell, base path and access token in a gitignored env file: `.env.local` (rust/golang/nextjs) or `.env` (python, python-decouple doesn't read `.env.local`). Go/Rust apps load it themselves on startup (godotenv/dotenvy), so launch configs carry no env and no token.
* `nova app update-env [path]` (`pkg/appenv`, `writeAppEnv` in `pkg/cmd/app.go`): always replaces the token (refreshed for `*.wandelbots.io`, empty otherwise), adds instance settings only if missing (`--reset` replaces them), keeps all other lines. `nova app create` runs it with reset. Variable names differ per template, see `appenv.Layout`.
* Instance ingress answers a missing/expired token with plain text `Error 401: Unauthorized` and **HTTP 200**; the Go/Rust templates check the content type and return 502 with a hint. Portal tokens last 24h.
* Python/novax registers its programs in the cell's program store under the app name from `BASE_PATH` (default `novax`) and removes them on shutdown: keep `BASE_PATH` unique when running locally against a shared instance.
* Verify template changes by generating with the built CLI (`bin/nova app create x -g <type>`) and running the app against an instance; `go test ./pkg/generator` only checks rendering.

## NovaFlow (`nova flow`)

* Code: `pkg/novaflow` (client), `pkg/cmd/flow.go`. Source of NovaFlow: `wandelbotsgmbh/novaflow` (Forest at `/<cell>/forest/trees`, control plane at `/<cell>/controlplane/api/v1`, editor at `/<cell>/flow`).
* Install = service-manager feature flag `GET/PUT /api/v2/internal/cells/{cell}/feature-flags` (`novaflow`, `novaflow_version`, read-only `novaflow_status`; flag API since service-manager 26.4, version/status since 26.8). Not in `nova-api-client-go`. **PUT replaces the whole object**: read-modify-write so `controller_connector` etc. survive (`FeatureFlags` keeps the raw fields).
* Verified live on a `nova virtual create` instance (service-manager 26.8.0) and a dev cloud instance (portal login reaches the internal flag API there too): install takes ~1 min; `disabled` is reported before the apps are gone, so uninstall also waits for Forest to stop answering; flows survive uninstall/reinstall (Forest keeps them in the object store). Versions other than the shipped one come from `oci://wandelbots.azurecr.io/helm/novaflow` and may not be pullable (401) — the old version keeps running, state `failed`, and the pin stays until `--version default`.
* **Portal (prod) instances don't expose `/api/v2/internal/*`** (service-manager Helm value `apiGateway.ingress.enableInternal`, set on dev only; the answer is 404 `{}`), and the public cell API has no NovaFlow switch. There `install` falls back to the `novaflow-installer` app from the **preview** catalog (`catalog.wandelbots.io/_preview/`): it deploys the NovaFlow apps through the public apps API and has a JSON API (`/<cell>/novaflow-installer/api/status`, `POST /api/install-all {"version"}`, `GET /api/readiness?version=`, `DELETE /api/uninstall-all`), see `pkg/novaflow/installer.go`. Its source repo is private; the image (`wandelbots.azurecr.io/ba/novaflow/novaflow-installer`) has `main.py`. `--installer` forces this path; once the app is on a cell, install/uninstall always use it. Never combine it with the flag on one cell (`install` refuses without `--force`). Verified on prod: install ~50 s, CI job `e2e-novaflow` runs `testdata/novaflow/e2e.sh` there. Dev portal instances are not reachable from GitHub runners.
* Ingress error pages arrive with **HTTP 200**: plain text `Error 401…`, or JSON `{"error": true, "code": 401, …}` when the request accepts JSON. Unauthenticated app paths answer 302 to `/oauth2/start`. `novaflow.Client` maps all three to `ErrUnauthorized` and doesn't follow redirects; never decode an answer without that check (a 401 page once decoded as "all flags false").
* Action services: `nova flow action create <name> [--action Name[:kind]]` (`pkg/cmd/flowaction.go`; deliberately not a `nova app create` generator for now) runs `uvx copier copy --trust --quiet` on `gh:wandelbotsgmbh/novaflow-action-template` (private for now: access is checked with `git ls-remote` first, copier would print a traceback). Interactive only with a terminal and no `--action`. Projects keep the copier link (`uvx copier update --trust`). The `.env` layout (`appenv.novaflowActionLayout`) writes `NOVA_API` **without** `/api` (the SDK appends `/api/v2`; the template's `.env.template` is wrong there), `CELL_NAME`, `NATS_BROKER=ws(s)://<host>/api/nats` and no token. Running locally only works against LAN/IPC instances (cloud rejects external NATS). Stopped services stay in the registry with `online_instances: 0`. Conditions are plain actions with a bool `result` tagged `condition` (the registry reports them as `operation_type: action`). Deploy = plain `nova app install .` (needs `uv.lock` from `uv sync`; the NOVA app operator injects `NATS_BROKER`/`NOVA_API`/`CELL_NAME`). The template's `.dockerignore` doesn't exclude `.env`, so it lands in the image (harmless here: no token, injected env wins).
* Backups (`nova flow backup`): `manifest.json`, `globals.json`, `flows/<id>.json`, optional `objects/<key>`. Restore order globals → flows → objects; existing items are kept unless `--overwrite`. The object store is the cell's NOVA store, shared with other apps. **Forest persists flows in it as `trees/<id>`** (its source of truth): object backup/restore skips that prefix, flows only go through Forest's API (caches, change events).

## Nucleus / Omniverse

* Nucleus servers are their own target, not part of an instance (ADR `docs/decisions/0018-nucleus-servers.md`): `nucleus-servers` (name, host, token, tls) + `current-nucleus` in the config, registry in `pkg/nucleusservers`, commands `nova nucleus server add/list/select/remove` (`pkg/cmd/nucleusserver.go`). Resolution: `--nucleus` (on `nova nucleus` and `nova config`, not global) → `NOVA_NUCLEUS` → `current-nucleus`. `nova nucleus` carries `annotationNoTarget`. `config set nucleus-host|nucleus-token` write the resolved server. A server's token is only sent to its own host: `--nucleus-host` to another host needs `--nucleus-token`/`NUCLEUS_TOKEN` (`nucleusConfig` in `pkg/cmd/nucleus.go`).
* Migration: the old `nucleus-host`/`nucleus-token` keys (instance entries, top level) become one server per host, named after the host (`nucleus.dev.wandelbots.io` → `dev`); the old keys stay for older binaries and are ignored once `nucleus-servers` exists. The migration is written before any instance-list write (`saveRegistry`), so removing an entry keeps its server. `--instance` with `config set nucleus-*` is an error (use `--nucleus`); `NOVA_INSTANCE` has no effect there.
* Protocol docs, reference JS bundles and how to fetch fresh ones: internal repo `wb-int/nucleus-api` (private, not part of this repo)
* Live test server: `https://nucleus.dev.wandelbots.io`
* Key gotcha: most connlib commands use **nested path objects** `{"path": {"path": "...", "branch": "..."}}`, not flat strings. See `protocol.md` in `wb-int/nucleus-api` for the exact schema per command.
* `create_directory` requires trailing `/` on paths or returns `INVALID_URI`
* `rename2` is the only file op that returns a stream; others return single response
* The ingress in front of LFT may replace 5xx/404 from the service with a plain-text error page served as **HTTP 200** (ingress-nginx `custom-http-errors` with an error-pages backend that defaults to 200). Never trust the status code of an LFT download alone — `ReadFile` verifies the body against the `size`/`hash_value` from the `read` response and retries (issue #41).
* The API WebSocket can die mid-session (laptop sleep, network change, proxy idle timeout). `connlib` reports that as `ErrClosed`; `List`/`ReadFile` re-dial and re-authenticate automatically (`Client.Reconnects()`), mutating ops surface the error instead.
* Request ids must reach the server in increasing order per connection, or it answers `INVALID_COMMAND` (same status as an unknown command). `Client.withCmd` allocates the id and sends under one lock; keep it that way when adding commands.
* The LFT service of a typical deployment is small: more than ~2–4 parallel large downloads push it into 5xx. Keep `-j` modest and don't load-test against a shared server.
* `hash_type: sha-256-flat` is **not** a plain SHA-256: split the file into `hash_bsize` blocks (1 MiB), SHA-256 each, then SHA-256 the concatenated raw digests (`nucleus.FlatHash`). A one-block file hashes to sha256(sha256(data)). Verified live; `protocol.md` in `wb-int/nucleus-api` doesn't document this yet.

## Simulation streaming (`nova simulation`, Wandelbots internal)

* Manages GPU streaming sessions (Isaac Sim, Blender) on the streaming session broker (dev: `https://broker.omni.dev.wandelbots.io`, viewer: `https://viewer.omni.dev.wandelbots.io/omniverse-stream`).
* The broker only accepts tokens of the viewer's **Microsoft Entra ID** app, not portal/Auth0 tokens from `nova login` (even though its spec says "NOVA access token"). `nova simulation login` runs the Entra device flow (public client, no secret) and stores the token under `simulation-token`, separate from the portal `token`.
* The same token authorizes the APIs inside a session: `https://<route host>:<kit port, default 8080>/wandelbots-stream/api/v1` and `/omniservice/api/v2`, each with an `openapi.json` (no hosted docs page; the viewer renders them itself).
* Code: `pkg/simulation` (client generated from the broker's `openapi.json`; `overlay.yaml` adds `type: string` to `LeaseStatus`, which the broker emits as `oneOf` + `const` without a type), commands in `pkg/cmd/simulation.go`. Only dev is configured in `environments`.

## MCP server (`nova mcp`, ADR-0019)

* Serves the toolsets of the instance MCP service's roadmap (service-manager MR !2924, `services/mcp/docs/roadmap.md` on code.wabo.run) locally over stdio until that service ships. The 8 tools in `pkg/mcp/tools.go` are ported unchanged from the MR; the toolsets in `pkg/mcp/toolsets/<name>` use the roadmap's names and rules so they can be upstreamed. `pkg/mcp/testdata/tools_snapshot.json` pins the surface (`UPDATE_SNAPSHOTS=1 go test ./pkg/mcp/` regenerates; review the diff).
* Shared code: `pkg/mcp/tool` (toolset names, default vs opt-in, annotations, `OK`/`Fail` result lines, `Page`, `Approval` for elicitation), `pkg/mcp/novaapi` (`Client`: plain HTTP to the v2 API with error mapping, ingress 200 pages, `RequireVirtual`/`RequireAllVirtual` gate). Response structs declare only the fields handed on, never connection details, credentials, env values or tokens. The published Go clients are older than the instances, so toolsets don't use them.
* Motion, I/O writes and mode changes only on virtual controllers (physical: `APPROVAL_REQUIRED`). `delete_cell`, `restore_backup`, `update_nova_version` go through `tool.Approval`. Server instructions in `pkg/mcp/instructions.go` (≤ 4096 chars, tested).
* Auth per call via `mcpSession.auth` (`pkg/cmd/mcp.go`): non-interactive `oauth.RefreshToken`, never a device login.
* Instance switching: `list_instances`/`use_instance` (`pkg/mcp/toolsets/instances`) exist only when the target isn't pinned by `--instance`/`NOVA_INSTANCE`. `mcpSession.Use` re-reads the registry, applies the instance's portal environment and calls `novaapi.Client.SwitchBaseURL`; nothing is written to the config. Per-instance state in toolsets (caches, registries) must be keyed by `Client.BaseURL()`.
* Live tests: `TestLive*` in each toolset, skipped unless `NOVA_MCP_LIVE_HOST` (+ `NOVA_MCP_LIVE_TOKEN=$(nova login token)`, `NOVA_MCP_LIVE_CELL`, `NOVA_MCP_LIVE_CONTROLLER` for a virtual controller, default `mcp-ur5e`) is set (`pkg/mcp/internal/livetest`). They only write to `mcp-test-*` resources they delete again; motion tests move the virtual controller.
* Smoke test: pipe `initialize`, `tools/list` and `tools/call` JSON-RPC lines into `bin/nova mcp`; stdout must carry only protocol messages.
